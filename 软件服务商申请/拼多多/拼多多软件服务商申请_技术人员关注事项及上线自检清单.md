# 拼多多软件服务商申请：技术人员关注事项及上线自检清单

> 整理日期：2026-07-27  
> 使用对象：技术负责人、产品经理、后端开发、前端开发、测试、运维、安全负责人  
> 申请主体：立成  
> 目标类目：订单管理、企业 ERP  
> OMS 软件著作权人：立成，已确认  
> 使用方法：技术负责人逐项确认，在“负责人、状态、证据”栏补充信息。状态统一填写：未开始 / 进行中 / 已完成 / 不适用 / 阻塞。

## 一、技术团队先确认的五件事

以下事项没有确认前，不建议直接开始申请接口权限或提交上线审核：

| 序号 | 事项 | 当前状态 | 需要谁确认 |
|---|---|---|---|
| 1 | 订单管理最终申请“打单”还是“订单处理”二级类目 | 待确认 | 业务负责人、产品经理 |
| 2 | 订单管理和企业 ERP 使用一个应用还是分别创建应用 | 以开放平台创建页面及审核意见为准 | 产品经理、技术负责人 |
| 3 | 实际申报应用名称、版本、功能与立成 OMS 软著是否对应 | 待核对 | 产品经理、法务/申请经办人 |
| 4 | 当前系统是否能接入多多云 | 待技术评估 | 架构师、运维 |
| 5 | ERP 是否真实具备 B/S、SaaS、多租户及每日 10,000 单处理能力 | 待验证 | 技术负责人、测试 |

## 二、平台明文技术门槛

### 2.1 两个类目的技术差异

| 检查项 | 订单管理 | 企业 ERP | 性质 |
|---|---|---|---|
| 技术人员 | 不少于 5 人 | 不少于 10 人 | 平台明文要求 |
| 客服人员 | 类目规范未单列数量 | 不少于 5 人 | 平台明文要求 |
| 订单处理能力 | 每日 1,000 单以上 | 每日 10,000 单以上 | 平台明文要求 |
| 多多云 | 必须接入 | 必须接入 | 平台明文要求 |
| 安全改造 | 加密接入、数据加密、前端解密接入风控等 | 加密接入、数据加密、前端解密接入风控等 | 平台明文要求 |
| 技术架构 | 规范未单独写明 B/S、SaaS | 必须采用 B/S 架构和 SaaS 模式 | 平台明文要求 |
| 重复应用 | 不得发布重复或类似应用 | 同一服务商同一类目只能发布一款应用 | 平台明文要求 |

技术团队需要配合提供人员名单、岗位和项目职责。劳动关系、社保等最终证明格式由申请经办人按后台要求准备。

### 2.2 订单管理最低功能

订单管理应用至少应完成：

- 订单处理。
- 订单分析。
- 物流发货。
- 拼多多电子面单打印。
- 售后管理。
- 商品信息管理。
- 商家上传和维护商品 ID、商品简称、规格 ID、规格简称、规格重量等信息。
- 商品信息一键导出。

注意：商品信息导出是平台明确要求的功能，但订单数据导出是禁止功能。开发和测试必须区分两种数据对象。

### 2.3 企业 ERP 最低功能

企业 ERP 至少应完成：

- 采购管理：供应商管理、采购询价、采购单跟踪、采购验收等。
- 销售管理：商品发布、店铺管理、销售报表、订单处理、退款退货、电子面单等。
- 库存管理：库存盘点、分析、共享、出入库、批次管理和库存预警等。
- 成本管理。
- 应收应付管理：应收单、应付单、收款单、付款单、应收应付核销和相关报表。
- 财务管理：财务对账分析和财务三大报表。

仅有 OMS 的订单、库存和发货能力，不代表已经达到企业 ERP 功能标准。采购、成本、应收应付、财务对账和三大报表缺一时，应先补齐或重新评估申报类目。

## 三、上线审核高风险禁区

以下项目应在代码、页面、配置和文档四个层面同时排查：

| 禁区 | 技术排查要求 | 结果 |
|---|---|---|
| 订单导出 | 删除或关闭订单导出为 Excel、CSV、文本等外部文件的入口、接口和隐藏配置 | 待查 |
| 店铺账号密码登录 | 不得要求商家向第三方软件输入或保存拼多多店铺账号、密码 | 待查 |
| 内嵌商家后台 | 不内嵌、不仿冒拼多多商家后台登录页 | 待查 |
| 未开放数据抓取 | 不使用爬虫、浏览器自动化、逆向接口等方式获取未开放后台数据 | 待查 |
| 评价返利 | 订单管理应用不得包含评价返利功能 | 待查 |
| 自动化跨平台铺货 | 不得在无人筛选情况下，按类目、关键词或定时任务自动上货并自动采购发货 | 待查 |
| 重复铺货 | ERP 不得生成或发布基本属性相同的重复商品 | 待查 |
| 跨渠道加价搬运 | ERP 不得将其他渠道基本属性相同的商品加价后发布到拼多多 | 待查 |
| 未完成版本 | 不提交原型、空页面、仅演示版本或尚未部署的版本 | 待查 |
| 申报不一致 | 实际功能、接口权限、审核文档和服务市场详情页保持一致 | 待查 |

代码中已经存在但前端暂时隐藏的违规功能仍有审核和运营风险。应从路由、接口、定时任务、权限配置和数据库任务中一起停用，而不是只隐藏按钮。

## 四、应用和接口权限设计

### 4.1 接口权限清单

技术负责人应建立“功能 - 接口 - 数据 - 页面”映射表：

| 业务功能 | 需要的平台接口 | 读取/写入 | 使用的数据 | 对应页面 | 申请理由 | 状态 |
|---|---|---|---|---|---|---|
| 店铺授权 | 待从开放平台确认 | 读/写 | 店铺授权信息 | 店铺绑定 | 建立商家授权关系 | 待填 |
| 订单处理 | 待从开放平台确认 | 读/写 | 订单及履约数据 | 订单中心 | 订单履约 | 待填 |
| 售后管理 | 待从开放平台确认 | 读/写 | 退款退货数据 | 售后中心 | 售后处理 | 待填 |
| 电子面单 | 待从开放平台确认 | 读/写 | 收件及面单数据 | 打单发货 | 物流发货 | 待填 |
| 商品信息 | 待从开放平台确认 | 读/写 | 商品和规格数据 | 商品中心 | 商品维护 | 待填 |
| ERP采购/库存/财务 | 平台接口与内部数据分别标注 | 读/写 | 采购、库存、成本、应收应付 | ERP模块 | ERP完整业务链路 | 待填 |

接口名称和权限包必须从申请主体的开放平台后台复制，不得凭第三方文档或其他平台的接口名称填写。

### 4.2 权限最小化

- 只申请已上线功能实际需要的接口权限。
- 每个权限都要有明确页面、操作人和业务场景。
- 不为未来可能开发的功能提前申请无实际用途的敏感权限。
- 读、写权限分别说明，写操作必须记录操作者、时间、对象和结果。
- 废弃功能对应的接口权限、任务和密钥应同步停用。

### 4.3 接口调用可靠性

以下属于工程建议，用于通过审核并保障上线后稳定运营：

- 写接口设置幂等键或业务去重机制，避免重复发货、重复退款或重复写入。
- 明确接口限流、超时、重试和退避策略。
- 区分可重试错误与不可重试业务错误。
- 回调事件验签、去重并记录处理状态。
- 调用失败进入可查询的异常队列，不静默丢弃。
- 关键任务具备人工补偿和重新执行能力。
- 接口日志不得直接记录完整身份证号、手机号、地址、密钥或访问令牌。

## 五、商家授权链路

上线前至少完成两条授权路径自测：

### 路径 A：从拼多多服务市场进入

```text
商家订购服务
→ 从服务市场进入应用
→ 跳转至立成应用
→ 商家确认授权
→ 应用接收授权结果
→ 店铺绑定成功
→ 商家进入可用功能页面
```

### 路径 B：从立成软件内部绑定

```text
商家登录立成软件
→ 选择绑定拼多多店铺
→ 跳转拼多多官方授权页面
→ 商家确认授权
→ 回调立成应用
→ 校验状态并绑定店铺
→ 显示授权范围和有效状态
```

### 授权自检

- 不收集拼多多店铺账号密码。
- 授权页面必须是拼多多官方页面。
- 校验回调参数和防重放参数。
- 授权令牌加密保存，不在浏览器地址、前端日志或错误信息中暴露。
- 明确授权到期、刷新、失效和重新授权流程。
- 明确商家主动解绑和平台撤销授权后的数据停止使用机制。
- 授权失败时显示可理解的原因和处理方式。
- 一个商家绑定多个店铺时，租户和店铺数据不得串用。

## 六、架构与安全

### 6.1 平台要求

- 接入多多云。
- 完成加密接入。
- 完成数据加密。
- 完成前端解密接入风控等平台要求的安全改造。
- ERP采用 B/S 架构和 SaaS 模式。

多多云的具体接入方式、安全组件和验收证据，应由技术负责人在开放平台后台获取最新要求后补入本清单。

### 6.2 建议形成的架构证据

- 系统架构图。
- 网络和部署架构图。
- 多租户数据隔离说明。
- 拼多多接口调用链路图。
- 商家授权时序图。
- 数据分类分级清单。
- 数据传输和存储加密说明。
- 密钥及令牌管理说明。
- 访问权限矩阵。
- 日志审计和告警方案。
- 备份、恢复和故障降级方案。

### 6.3 数据安全自检

- HTTPS覆盖所有生产页面、接口和回调地址。
- 密钥、访问令牌不写入代码仓库或前端包。
- 数据库中的令牌和敏感数据加密存储。
- 前端只展示当前操作需要的数据。
- 用户、店铺、租户之间进行严格权限校验。
- 测试环境不使用真实商家数据，确需使用时进行脱敏。
- 管理后台高风险操作进行二次确认并留痕。
- 商家解绑、授权到期和服务终止后停止继续拉取数据。
- 制定数据保存期限、删除和商家请求处理机制。

## 七、容量与稳定性测试

### 7.1 审核门槛

- 订单管理：证明每日可处理 1,000 单以上。
- 企业 ERP：证明每日可处理 10,000 单以上。

### 7.2 建议测试场景

| 场景 | 需要验证 | 证据 |
|---|---|---|
| 批量拉取订单 | 分页、限流、断点续传、重复数据 | 测试报告、日志截图 |
| 高峰订单处理 | 峰值吞吐和任务积压恢复 | 压测报告 |
| 批量打单发货 | 面单获取、打印、发货状态一致性 | 测试记录 |
| 售后并发 | 退款退货状态同步 | 测试记录 |
| 接口超时 | 重试、降级、告警 | 故障演练记录 |
| 回调重复或乱序 | 幂等、顺序校正 | 自动化测试结果 |
| 服务重启 | 未完成任务恢复 | 恢复记录 |
| 数据库故障 | 备份、恢复、只读或降级策略 | 演练记录 |

测试报告应写清测试环境、数据量、持续时间、通过标准、实际结果和问题处理，不只提供一张成功页面截图。

## 九、提交上线前测试用例

### 9.1 基础与授权

- 新商家从服务市场进入并完成授权。
- 已有用户从立成软件内部绑定店铺。
- 授权取消、拒绝、超时和回调失败。
- 授权过期和重新授权。
- 主动解绑后停止数据调用。
- 多店铺切换时数据不串店。

### 9.2 订单管理

- 新订单同步。
- 订单查询、筛选和分析。
- 发货和电子面单打印。
- 发货失败及重试。
- 退款、退货和售后状态同步。
- 商品及规格信息维护。
- 商品信息导出。
- 确认不存在订单导出。

### 9.3 企业 ERP

- 供应商、询价、采购单和采购验收流程。
- 商品、店铺、订单、退款退货和电子面单流程。
- 入库、出库、盘点、批次和库存预警流程。
- 成本计算。
- 应收、应付、收付款和核销流程。
- 财务对账。
- 资产负债表、利润表、现金流量表或平台认可的财务三大报表。

### 9.4 安全和异常

- 越权访问不同租户或店铺数据。
- 修改店铺 ID、用户 ID 等参数尝试越权。
- 令牌失效、接口限流和平台接口异常。
- 重复提交写操作。
- 回调重复、乱序和伪造。
- 敏感信息在页面、接口响应和日志中的脱敏。
- 系统故障后的告警、降级和恢复。

## 十、上线审核流程中的技术动作

```text
确认类目和应用形态
→ 创建应用
→ 申请接口权限
→ 接入多多云
→ 开发类目必需功能
→ 完成安全改造
→ 部署正式审核版本
→ 完成两条授权路径
→ 功能、容量、安全自测
→ 准备测试账号和审核说明
→ 提交应用上线审核
→ 处理驳回意见
→ 重新测试并提交
→ 应用上线
→ 配合发布服务市场商品
```

每次驳回都应建立记录：

| 日期 | 审核环节 | 驳回原文 | 原因归类 | 修改内容 | 负责人 | 回归测试 | 再提交日期 |
|---|---|---|---|---|---|---|---|
| | | | 功能/权限/授权/安全/材料/类目 | | | | |

禁止只修改文案后直接重新提交。涉及代码、权限或流程的驳回项必须完成回归测试。

## 十一、上线后的技术监控

上线后需要持续监控：

- 有效授权店铺数。
- 每日 API 调用量、成功率、错误类型和限流情况。
- 每日同步订单数和日均发货订单量。
- 授权到期、授权失败和无效店铺数。
- 订单、发货、售后和库存同步延迟。
- 关键任务积压量。
- 每个应用功能故障或缺失导致的投诉数量。
- 服务可用性和严重故障时长。
- 最近一次商家订购时间。
- 最近一次 API 调用时间。

监控需要支持以下风险预警：

- 订单管理每月交易收入低于 200 元。
- 订单管理考核周期订购店铺少于 5 家。
- ERP上线满3个月后授权店铺或日均发货量接近考核下限。
- 30日无新增订购的隐藏风险。
- 60日无新增订购的冻结风险。
- 90日未调用 API 且无有效授权用户的清除风险。
- 投诉介入量接近每季度3起。

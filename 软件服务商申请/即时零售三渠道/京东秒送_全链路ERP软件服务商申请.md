# 京东秒送全链路ERP软件服务商申请

> 京东官方页面对应名称为“全链路解决方案”。本文件按友联内部理解称为“全链路ERP”，与订单管理单项工具分别核算和申请。

## 一、能力范围

面向京东秒送的外卖、到店及即时零售商家，提供包括以下模块在内的全链路解决方案：

- 店铺及门店管理
- 商品管理
- 订单与收银
- 配送履约
- 营销与会员
- 客服管理
- 品牌总部到门店的经营管理

该申请目标强调多模块一体化和行业解决方案能力，不等同于仅处理订单、打印、售后单的订单管理工具。

| 技术团队 | 不少于20人 |

11. 中长期研发、销售、运营和服务计划。

### 5个成功服务案例的理解及准备方法（2026-08-13复核）

#### 1. 结论

京东要求的“5个以上成功服务案例”不应理解为5个已经调用京东秒送正式API的客户案例，而应理解为申请企业在入驻前已经完成的餐饮或即时零售行业ERP实施案例。

京东官网原文将案例要求放在以下能力要求之后：申请企业应对餐饮或即时零售商家的商品、门店、交易、履约等领域具备产品能力、行业化深度服务能力和深度服务经验，并提供主要服务行业列表、服务体量、5个以上成功服务案例及至少1个标杆客户实施成功详细案例。原文没有写“京东秒送案例”或“已调用京东接口的案例”。

京东公开入驻流程同时显示：先提交类目资质资料并接受审核，审核通过后再缴纳保证金、获得服务商工作台权限、发布服务并完成服务上线。案例属于准入资料，如果反过来要求申请前已经通过正式接口服务5个京东秒送客户，会与该入驻顺序形成循环。因此，案例的作用是证明申请主体已有行业产品和实施能力，而不是证明已取得京东接口权限。

“其他平台案例可以使用”是根据上述原文和流程得出的合理解释；京东官网没有单独发布全链路案例模板，也没有明确列举哪些其他平台案例必然通过。因此，其他平台、关联公司、同集团多品牌和同一客户多个项目如何计数，仍应取得京东秒送运营或审核人员书面确认。

#### 2. 原则上可以准备的案例

- 餐饮连锁品牌的点餐、收银、订单和配送系统；
- 药店、商超、便利店、生鲜门店的即时零售ERP；
- 品牌总部到门店的商品、库存、交易和履约管理项目；
- 已对接美团、淘宝闪购或其他即时零售平台的ERP项目；
- 线下POS、OMS、ERP、WMS与即时配送协同项目；
- 品牌私有化部署或已经实际投入使用的SaaS项目；
- 尚未接入京东秒送，但已经真实运行并处理门店、商品、订单、库存及履约的项目。

以上案例应由申请主体真实签约、实施或持续服务。关联公司案例不是当然可以使用；如确需引用，应准备股权关系、项目参与证明、客户授权及申请主体实际承担研发或服务工作的证明，并在申报前让京东确认。

#### 3. 风险较高或不能作为有效案例的情形

- 只有产品演示、原型、沙箱测试或内部测试，没有真实客户；
- 只有合作意向书，项目尚未上线；
- 将同一个客户的5个功能模块拆成5个案例；
- 只有软件销售发票，没有合同、实施、验收或实际使用证据；
- 纯传统电商案例，无法体现门店、即时订单及履约能力；
- 其他公司独立完成的案例，申请主体没有合同、研发或交付关系；
- 同一集团下多个品牌或门店被简单拆分计数，但没有独立合同或实施边界；
- 虚构客户、合同、截图、订单量或经营数据。

京东没有公开同一集团多品牌、同一客户多个独立项目的计数规则。最稳妥的方案是准备5个相对独立的客户主体或5个边界清晰、分别签约和验收的实施项目。

#### 4. 五个案例应共同证明的产品能力

案例组合应能够证明申请企业在以下领域具有真实产品和交付能力：

- 商品及类目管理；
- 门店及品牌总部管理；
- 交易、订单和收银；
- 库存及供应链；
- 配送和履约；
- 售后和客服；
- 营销及会员；
- 多门店经营分析。

官网没有要求每一个普通案例都覆盖全部模块，但5个案例组合应覆盖商品、门店、交易、履约四个核心领域；至少1个标杆案例最好能够体现较完整的全链路能力、多门店规模和真实订单履约。

#### 5. 每个普通案例建议材料

| 材料 | 建议内容 |
|---|---|
| 客户信息 | 客户公司、品牌、行业、门店数量及合作主体 |
| 项目背景 | 客户原有问题、建设目标及选择本系统的原因 |
| 服务时间 | 合同、实施、上线及持续服务时间 |
| 服务范围 | 商品、门店、订单、库存、履约、会员、客服等模块 |
| 服务体量 | 品牌数、门店数、账号数、日订单量、累计订单量等 |
| 合同证明 | 软件合同、实施合同、SaaS服务合同或订单 |
| 交付证明 | 验收单、上线确认书、客户盖章证明或续费记录 |
| 收款证明 | 发票或回款记录，可按审核需要脱敏 |
| 产品证明 | 登录页、客户账号、功能页面、架构及业务流程截图 |
| 使用证明 | 门店、商品、订单、库存及履约统计截图，消费者数据必须脱敏 |
| 客户评价 | 推荐信、客户盖章说明、续费或持续服务证明 |

普通案例建议每个形成3至5页材料。京东秒送全链路页面没有公开规定固定页数，页数属于内部材料组织建议。

#### 6. 标杆客户详细案例建议结构

1. 客户主体、品牌及行业背景；
2. 门店规模、业务范围和服务体量；
3. 上线前的经营和系统痛点；
4. 系统总体架构及部署方式；
5. 商品、门店、订单、库存、交易和履约流程；
6. 实施团队、项目计划和上线周期；
7. 已上线系统的真实功能截图；
8. 上线前后效率、稳定性或经营指标变化；
9. 合同、验收、回款、客户证明或续费材料；
10. 后续运维、客服、故障响应和持续服务体系。

标杆案例建议单独形成15至30页的详细材料。不得提交其他平台消费者的姓名、手机号、地址、处方或完整订单等个人信息；订单和交易截图应脱敏，只保留审核产品能力所必需的汇总数据。

#### 7. 如果目前不足5个真实案例

如果申请主体完全没有5个真实餐饮或即时零售项目，按当前公开规则暂不满足全链路解决方案类目的案例门槛，不能依赖取得京东接口后再补齐，也不能通过虚构材料绕过。

可以采取的路径包括：

- 盘点公司现有餐饮、药店、商超、便利店、生鲜等ERP客户，补齐合同、验收、截图和服务体量材料；
- 先完成真实客户实施并取得可核验的交付和使用证明；
- 评估独立申请“订单SAAS/交易履约”等门槛相对较低的秒送软件类目。当前规则没有对订单SAAS明确列出5个案例，但其属于独立类目，不代表可以自动升级为全链路资质，后续申请规则需另行确认。

#### 8. 建议向京东书面确认的问题

建议通过工单、邮件或运营沟通记录提交以下问题并保留回复：

> 我司拟申请京东秒送“全链路解决方案”软件服务商。准入规则要求提供5个以上成功服务案例及1个标杆客户详细实施案例。请确认：申请主体在京东秒送以外已经实施上线的餐饮、药店、商超等即时零售ERP项目，能够提供服务合同、验收证明、系统截图及门店和订单体量证明的，是否可以作为准入案例？如可以，请确认案例材料模板、是否要求5个独立客户主体、同集团多品牌如何计数，以及关联公司案例能否使用。

在取得书面回复前，内部统一口径为：5个案例是申请主体既有的餐饮或即时零售ERP成功实施案例，不要求预先调用京东秒送接口；其他平台案例具有合理申报基础，但是否最终接受以京东审核结果为准。

## 五、待确认

1. 全链路解决方案是否属于定向邀约。
2. 友联现有ERP功能是否达到“全链路”审核口径。
3. 全链路ERP是否必须同时具备商品、订单、履约、会员和客服全部模块。
4. ISO27001是否为强制要求，还是可由同等安全认证替代。
5. 申请全链路ERP后，是否仍需另行申请订单管理和客服类工具资质。
6. 同一企业不同软件类目是否需要使用独立企业账号。
7. 全链路ERP的京东API调用、京东数据和订单履约逻辑是否必须部署在云鼎，以及具体部署边界。
8. 其他平台的餐饮或即时零售ERP案例是否可计入5个案例；关联公司、同集团多品牌和同一客户多个项目如何计数。
9. 5个普通案例及1个标杆案例的材料模板、必需证明和脱敏要求。

## 七、取得资质后的部署和运行费用（2026-08-13复核）

### 1. 平台费用

- 服务市场保证金为50,000元。保证金属于履约担保和资金占用，正常退出且无违规、纠纷或赔付时可按规则申请退回。
- 当前运营支持服务费为0%。
- 服务商不得以京东JDO秒送开放平台收取保证金或要求安全资质为由，向商家宣称平台接口收费。

### 2. 云鼎部署规则冲突

京东当前公开规则存在两层口径：

- 新版秒送类目标准在全链路ERP一栏仅明确要求购买系统所在云服务器的WAF；“应用和数据需要部署在京东云鼎内”只在会员或营销互动类目中明确列出。
- 京东通用《接入规则与安全规范》仍要求JDO应用入驻云鼎、API调用从云鼎发起、京东数据在云鼎内存储和使用，并要求ERP订单履约业务逻辑在云鼎内运行。

因此，不能据类目表省略直接认定全链路ERP已豁免云鼎。未获京东秒送运营或开放平台书面确认前，应：

1. 预算中保留云鼎云主机、云数据库、网络及安全产品费用；
2. 架构上预留京东API调用、京东数据和订单履约逻辑在云鼎内隔离部署；
3. 正式采购前通过工单、邮件或协议确认部署范围、数据边界和资源规格。

### 3. 企业自行承担的持续成本

- 云鼎或其他经确认云环境的云主机、数据库、存储、流量；
- Web应用防火墙；
- 等保二级备案、测评及后续复测；
- ISO体系认证及监督审核；
- 日志审计、监控告警、备份、容灾和安全运维；
- 产品研发、客服、实施和商家运营团队成本。

三渠道完整对比见：[申请助手.md](./申请助手.md)。

## 八、取得资质后的经营与业绩要求（2026-08-13复核）

### 1. 是否存在明确的增长硬指标

截至本次复核，京东公开的《秒送软件服务商入驻及运营规范-新》没有规定全链路ERP取得资质后必须实现固定的月度或季度GMV增长率，也没有公布最低新增商家数、最低绑定门店数或最低订单处理量。

但取得资质不等于永久保留：平台存在经营活跃度治理和服务评分机制，长期没有销售、评分过低或经营停滞，可能导致服务下架、类目关闭或无法续签。

### 2. 明确的经营底线

- 开发者应在规定时间内开发并上线产品；规范要求3个月内启动开发，未按期完成上线的，平台有权收回应用权限。
- 2026年1月发布的治理通知将“经营停滞服务商”定义为：旗下所有服务均在2025年以前发布，且近1年服务市场成交单量为0。
- 命中经营停滞治理的服务商会被取消类目资质并下架服务；退出后至少经过6个月观察期才可重新申请。
- 平台后续按月对近一年无销售服务和经营停滞服务商进行治理。

该“近一年成交单量为0”是当前公开可确认的最低经营底线，不等同于平台要求实现某个增长率。该治理公告覆盖互动、订单、商品、内容技术、客服、广告、CRM等ISV工具线；秒送全链路ERP是否按相同口径执行，仍应在入驻或续签时向秒送运营确认，但不建议以零销售状态长期维持资质。

### 3. 影响评分、流量和续签的业绩指标

JDM服务市场的总体评分指标池包括以下经营指标：

- 近30天订购转化率；
- 近90天服务市场成交金额及有效服务报备金额；
- 近90天成交订单量及有效服务报备量；
- 付费商家渗透率；
- 服务启动率；
- 服务续费率；
- 用户评价评分；
- 覆盖商家GMV；
- 服务商家数量；
- 咚咚60秒人工应答率、资料完整度、安全分和质量评估分等。

各类目实际启用的指标不同。当前官方表格对“软件服务”明确勾选的主要项目是资料完整度、服务考试、咚咚60秒应答率、订购转化率、安全分、付费商家渗透率、启动率、续费率、用户评价、质量评估分和京麦端TP90；成交金额、成交订单量、覆盖商家GMV和服务商家数属于总体指标池及运营提升参考，当前表格没有全部明确勾选为软件服务考核项，不能直接表述为全链路ERP硬考核。

平台未为全链路ERP公开上述指标的统一最低数值，但明确说明服务评分与搜索权重、广告申请、平台推荐、审核时效、接口权益和续签关联；评分低的服务会逐步淘汰，续签时评分低可能无法续签。

### 4. 内部建议经营目标（非官方硬门槛）

- 上线3个月内至少形成真实付费或有效报备订单，避免长期零成交。
- 持续维护真实服务商家数、活跃门店数、成交金额、成交订单量和续费率。
- 线下签约客户及时通过京东认可的服务报备系统进行有效报备。
- 每月监控服务评分、咚咚60秒应答率、投诉、系统稳定性和用户评价。
- 每季度形成客户增长、覆盖门店、订单处理量、续费及标杆案例复盘材料，用于平台抽查和续签。

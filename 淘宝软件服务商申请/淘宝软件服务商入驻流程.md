# 淘宝软件服务商入驻流程（官方入口）

更新于：2026-07-27（按淘宝开放平台官网文档）
来源：[`应用软件开发商-接入指南`](https://open.taobao.com/doc.htm?docId=120867&docType=1)（文档页路径：`https://developer.alibaba.com/docs/doc.htm?articleId=120867&docType=1`）

## 一、入驻成为生态伙伴

- 第一步：打开淘宝开放平台官网首页并进入入驻入口。
  - 官网：`https://open.taobao.com`
- 第二步：用淘宝账号登录，完成支付宝绑定与实名认证，选择“企业身份入驻”。
  - 支付宝绑定的账户需与淘宝账号一致。
- 第三步：选择“应用软件开发商”身份。
  - 适用场景：提供小程序、商品、订单、交易、营销、物流、广告、店铺、数字化经营等核心业务场景的 IT 系统应用。
  - 一个账号可申请多个身份，完成一个后可在“设置-基础信息”补充。
- 第四步：按引导完成风控安全扫描、企业资料、实人认证、资金管理服务开通。
  - 可先跳过“实人认证/资金管理服务开通”，在发布服务/上架售卖时补齐。
- 第五步：入驻成功后进入生态伙伴工作台。

### 文档澄清（你提到的 121810）

- `docId=121810` 对应的是“应用软件开发商-开放类目招商入驻指南”。
- 这个页面是**两层结构**，前半是“淘宝购物小程序”，后半是“商家经营工具”。
- 我们目前应按**商家经营工具**路径走（与 ERP/订单管理一致）。
- 也就是优先看页面中的【二、商家经营工具】与类目规则，而不是“购物小程序”部分。

### 为什么“客服ISV服务”在你看到的页面里不明显？（直接回应你这次提问）

- `docId=121810` 是“开放类目招商入驻指南”的入口页，不是每个类目的完整要求正文。
- “客服 ISV”对应的是独立的类目页/规则，当前在文档树里通常以**客服工具**入口出现（不是总入口里的主表格里会展开所有条款）。
- 例如：
  - [客服工具发布规则（docId=120818）](https://developer.alibaba.com/docs/doc.htm?articleId=120818&docType=1&treeId=782)
  - 历史/扩展说明可见“客服工具类目管理规范”变更内容（较早版本在其他入口发布）
- 所以你没看到“客服ISV服务”多数是：
  - 看的是“入驻总览页”（如 121810），
  - 或你点开的是“订单/ERP”导向分支，
  - 而没有再点入“客服工具”具体类目。

#### 实务结论（便于你们决策）

- 你们当前目标是 ERP + 订单管理，先围绕 121765 / 121762 做，不建议把“客服工具”混入同一次主类目申请。
- 如果以后要做客服方向，按**客服工具类目**独立走一条申请线，避免类目边界混淆。

#### 对应关系（你要避免的误选）

1. 误选风险：把目标当成“购物小程序”
   - 对你们 ERP/订单管理不匹配。

2. 正确路径：商家经营工具
   - 研发方式可选：`千牛商家应用` 或 `一站式电商后台`。
   - ERP/订单类重点看：
     - 一站式电商后台中的【企业ERP】类目（支持商品、库存、交易、物流等电商业务）
     - 电商管理中的【订单管理】等相关类目

3. 可复核点（来自官方文档）
   - 商家经营工具定义：面向商家做店铺运营管理与营销工具，发布于服务市场的第三方 ISV 应用。


### 我们这类场景：商家经营工具（ERP / 订单管理）明确建议

- 入驻身份：仍然是“应用软件开发商”。
- 业务类型：在“开发-创建应用”第一步请选择【商家经营工具】。
- 适合类目方向（可并行规划）：
  - 商品管理
  - 商品供应链服务
  - 内容创意（如需）
  - 客户服务
  - 流量推广（如需）
  - 客户关系管理
  - 企业数字化经营（ERP/订单管理通常放在该方向）
- 对审核最敏感的点：你要能证明有完整闭环，而不是只读工具。
  - 至少涵盖：订单审核、转单、发货、通知配货、售后受理与更新。
  - 软著/系统说明/源码截图与应用场景命名需一致（避免“应用叫 ERP，功能却像导出查询系统”。）

### 商家经营工具提交材料（简版核验清单）

1. 企业与身份材料
   - 企业实名认证
   - 银行与支付宝对应关系一致性
2. 类目材料（按类目要求）
   - 计划研发方案
   - 方案图/流程图（含订单闭环）
   - 资质材料
3. 系统真实性材料（关键）
   - 软著（命名与功能口径一致）
   - 系统功能说明书（模块、流程、架构）
   - 源码片段（关键链路）
   - 功能截图（订单审核、订单流转、发货、售后）
   - API 调用说明
4. 说明性建议
   - 有售卖资质：重点补齐类目方案。
   - 无售卖资质：同时补齐方案与资质材料。

### 一般建议（避免踩坑）

- 先做“最小闭环”再扩权限：`商品管理 -> 订单管理 -> 物流回传 -> 售后处理`。
- 提前对齐“类目入驻审核规则”与“服务审核标准”的文档要求。
- 平台风控口径关注“是否真实自研、是否可核验、是否仅供自家店铺使用”。

## ISV 与奇门：关联性与差异性（ERP/订单管理场景）

### 怎么理解两者关系

- `ISV 入驻`：是淘宝开放平台的**身份与商业化入口**，用于发布/售卖应用、申请淘宝 API 权限、接入店铺经营场景（订单/商品/物流/售后等）。
- `奇门`：是`聚石塔`内外系统标准化对接能力，是`ERP/WMS/POS`等系统之间消息和接口的**标准化互通层**。
- 简单说：
  - ISV = 你“向平台申请应用能力”和“对接淘宝能力”的通道。
  - 奇门 = 你“把自研 ERP 与 WMS/POS/财务系统打通”的标准协作通道。

### 为什么两者都会出现

- 你申请的是“商家经营工具（ERP/订单管理）”，核心闭环是面向店铺与淘宝订单的业务。
- 一旦还需要接入 `ERP-WMS`、`ERP-POS` 或 `线上 ERP-线下 OMS` 等系统协同，奇门可减少对接方标准差异成本。
- 实操上常见的是：
  1. 先完成 ISV 入驻（身份+应用+类目）
  2. 再按场景在奇门侧创建场景/appkey 进行系统互通
  3. 两条路径互补：一个负责“能否拿到淘宝端能力”，一个负责“系统内多端协同能力标准化”。

### 关键差异

- 审核目标不同
  - ISV 更看重：应用身份、软著与系统说明一致、功能闭环、平台服务市场合规。
  - 奇门更看重：场景角色、场景绑定、调用链是否按标准路由，及 appkey 映射关系。
- 接口对象不同
  - ISV：访问淘宝开放 API（商品、订单、交易、物流、客服等），支持对外提供应用服务。
  - 奇门：做系统间标准消息/接口映射（ERP-WMS 等），不等于淘宝 API 直接替代。
- 使用场景对象不同
  - ISV 面向“店铺/服务市场”。
  - 奇门面向“企业内部或生态系统内多个软件系统打通”。
- 成本特征不同
  - ISV 调用有 API 计费与调用量治理。
  - 官方说明中奇门互通接口本体偏免费，但仍需按平台流程进行授权与验收。

### 对我们申请路径的建议

- 先以 ISV 为主线完成申请：商家经营工具 → ERP/订单管理闭环。
- 若涉及多系统对接（如仓库系统/财务系统），同步走奇门（按 `开发者自定义/场景` 机制）做协议化接入。
- 避免把奇门理解成“替代性”的资格审核：
  - 你既要有淘宝侧接口接入（ISV 逻辑），
  - 也要有系统打通侧的标准对接（奇门逻辑）。

## 企业ERP类目（你发的 121765）重点要求提要

这是商家经营工具里“**企业ERP**”的正式类目规则，适合我们这类场景。要点如下：

### 1) 功能覆盖要求

- 必须覆盖电商链路关键模块：
  - 订单管理：订单处理、订单审核、订单发货
  - 商品管理：商品信息维护
  - 采购管理：从询价到采购结算
  - 库存管理：库存同步、库存分析、出入库、库存批次
  - 售后管理：退换管理
  - 财务管理：对账/资金/账款/核算/成本/电子发票
- 以下为可选模块：企业内部管理（人力/OA/流程）、仓储管理（分拣/货位/仓内作业）

### 2) 入驻硬性门槛

- 支付宝企业认证 + 企业注册 >=2年
- 注册资本 >= 1000 万元
- 经营范围要包含软件设计开发
- 不得是平台清退主体及其关联方
- 规模约束：
  - 团队规模 >=100 人
  - 技术团队 >=20 人
  - 要有运营与服务团队
- 需提供：ERP 软著、ISO27000/ISO27001 相关体系资料（或同类可核验能力证明）
- 要有商家化产品能力与行业化服务经验：给出主要服务行业、客户量、服务体量
- 至少 5 个标杆客户案例（至少 1 个详细成功案例）
- 提供完整 MRD/PRD（用户分析、产品规划、功能说明、主流程、研发计划、销售目标、组织与长期运营等）
- 具备订单全链路监控能力，回传订单作业数据（如订单转单、通知配货、库存查询、仓库作业节点）
- 接入订单处理链路消费者信息保护方案（涉及个人信息要加密/去标识化）
- 应用支持订购模式：按订单量或按周期买断（建议按订单量）
- 支付服务市场保证金：200,000 元
- 仅 B/S 架构（非 C/S 客户端）

### 3) 审核与上架后的常见风控边界

- 功能需与类目边界一致，未授权不要跨类目开发发布
- 上线服务详情页需完整（场景说明、教程、案例、售后流程）
- 应用不得泄露平台接口数据给第三方，需遵守相关安全与违规规范

### 4) 考核机制（避免落在“可做可不做”）

- 企业ERP有季度考核；未达标会触发清退风险
- 通用型基线（常见理解）：新增订购/续订商家与日均订单处理发货量需要满足基础阈值
- 行业型 ERP 需要维持单行业订单占比>=50%，否则转通用型
- 连续两次季度未达标会触发清退（清退后 180 天不能重新申请）

### 5) 与我们项目的落地理解

- 对我们是正向匹配项：ERP/订单管理是“企业ERP”核心场景
- 现实执行时优先把“企业规模、软著、MRD/PRD、订单全链路回传、信息安全”这四块做成可复核清单
- 这会明显提高类目审核通过率和后续季度稳定性

## 订单管理类目（你发的 121762）重点要求提要

这是“商家经营工具”下的订单管理方向，和企业ERP不是同一条线。

### 1) 二级类目与能力边界（别跨界）

- 包含：
  - 交易管理（插件）：订单展示、改址、核对订单、订单备注、合单、订单搜索
  - 打单发货：面单/发货单/配货单打印、发货、电子面单、面单模板
  - 商品管理：商品简称设置
  - 售后管理：退换货处理、评价管理
- 客户范围：服务淘宝商家、天猫商家

### 2) 入驻条件（关键）

- 资质与规模（相对 ERP 更轻一点）：
  - 支付宝企业认证通过
  - 注册年限 >= 2 年
  - 注册资本 >= 500 万元
  - 经营范围包含软件设计与开发
  - 企业、技术、运营团队规模：
    - 总规模 >=30 人
    - 技术团队 >=15 人
- 能力与材料：
  - 有订单管理开发经验
  - 提供软件著作权、ISO27000/ISO27001 相关资料
  - 有订单、履约方向的产品能力与用户规模
  - 付费订单（非试用）需 >= 1000 单（含其他开放平台订单管理类应用订购数据）
  - 提供 MRD/PRD（用户分析、产品规划、功能描述、流程、研发/运营计划等）
  - 提供 >=5 个标杆案例 + 至少 1 个详细成功案例
  - 具备订单全链路监控能力，订单作业数据与平台双向对接
  - 支持“使用端入千牛”的云端一体模式
  - 接入消费者信息保护方案（加密/去标识化）
  - 遵循应用质量管理规范，按时完成标准化改造与评分要求
  - 完成订单类目对接功能改造（安全/业务）
- 服务市场保证金：50,000 元

### 3) 上线与运营规范（审核高频被拦点）

- 必须是 B/S 架构，不支持 C/S 客户端
- 服务详情需完整：
  - 功能与场景说明
  - 后台操作说明（图文/视频）
  - 售后服务与联系方式
  - 旺旺保持在线（售后响应）
- 多版本应用要有版本功能对比
- MRD/PRD 核验点：
  - 创新性与差异化
  - 实用性、安全性
  - 接口调用与功能模块说明
  - 团队配置合理性（开发+产品+运营）
- 不得超范围发布未开放功能（例如超出类目定义）
- 不得未授权将平台数据外泄给第三方

### 4) 考核机制（比 ERP 更“运营驱动”）

- 考核周期：月度，首次上线后前 3 个月可免考核
- 经营考核：
  - 指标：订购商家规模 + 成交 GMV
  - 商家规模需达到类目前 95%（相对名次）
  - 成交 GMV >= 10000 元（按月）
- 服务考核：
  - 月度服务投诉率 <= 2%
  - 旺旺 3 分钟响应率 >= 80%
  - 应用质量抽检：骚扰弹窗 <= 2 次
- 未达标处置（重点）：
  - 累积多期未达标会触发冻结（先7天/1个月/服务冻结）
  - 严重持续不达标进入清退流程

## 二、创建应用

- 第一步：进入“开发-创建应用”，先选业务类型。
  - 淘宝购物小程序（偏商家服务消费者的轻量应用）
  - 商家经营工具（偏商品管理、供应链、内容、客户服务、流量推广、CRM、企业数字化经营）
- 第二步：选择类目。
  - 可按类目或按投放场景选择（店铺首页、会员中心、直播等）。
  - 有售卖资质的账号仅提交研发方案；无售卖资质需同时提交方案与资质材料。
- 第三步：提交相关资料申请类目权限。
  - 先阅读《类目入驻审核规则》后再提交，提升通过率。
  - 包含“方案申请 + 资质申请”。
- 第四步：等待平台审核（通常 5-10 个工作日）。
  - 可在工作台“支持-审核流程”查看进度。
- 第五步：按开发指引继续配置并进入开发。

## 三、发布服务（上架售卖）

- 第一步：在“开发-我的应用”中选择已完成应用，点击“上线售卖”，选类目发布。
- 第二步：填写服务详情页与收费信息（建议先读《服务审核标准》）。
  - 支持最多 10 个收费项目。
- 第三步：提交服务审核（约 5 个工作日）。
- 第四步：发布后在“运营-服务列表”管理服务。
- 第五步：审核通过自动上架至服务市场。
